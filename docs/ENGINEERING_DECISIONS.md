# Engineering decisions

1. **Relational model with append-only history.** *Context:* work items change often and every change must be explainable. *Alternatives:* event sourcing; JSON audit blobs. *Chosen:* normalised tables plus `activity_events`, written only inside the mutating transaction, and made append-only by a database trigger. *Why:* simple to query and to defend; the database, not convention, guarantees history cannot be edited. *Trade-offs:* history is not a full state log. *At scale:* partition events by time.
2. **Atomic claim and optimistic locking.** *Alternatives:* `SELECT … FOR UPDATE`, an application mutex. *Chosen:* single conditional UPDATEs (`assignee_id IS NULL`, `version = $n`); zero rows -> 409. A PATCH that changes nothing writes nothing (no version bump, event or job), and unknown fields such as `status` are rejected with 422 instead of ignored. *Why:* one statement is atomic without holding locks across round trips; rejecting unknown fields makes bypass attempts visible. *Trade-offs:* clients must send `expectedVersion` and handle 409. *At scale:* unchanged; contention is per item.
3. **Resource-level authorization.** *Chosen:* every item query joins `memberships`; non-members get 404 (existence hidden), members without the role 403. Roles are per team and read from the database on every request. *Why:* the policy lives in one function and is covered by a role x route matrix test. *Trade-offs:* one join per request. *At scale:* cache memberships, consider row-level security.
4. **Idempotency.** *Chosen:* unique (actor, scope, key) with a SHA-256 of the payload, written in the creation transaction; replay returns the stored response; 24-hour retention enforced by treating older rows as absent and purging them on reuse. *Alternatives:* a Redis cache (extra infrastructure). *Trade-offs:* no background purge, so abandoned keys accumulate until reused. *At scale:* a scheduled purge job.
5. **Synchronous transaction vs asynchronous outbox.** *Chosen:* the side effect is queued in the same commit and processed by a separate worker with leases, capped exponential backoff, a maximum attempt count, permanent-failure support and redacted errors. Delivery is at-least-once with an idempotent sink. *Alternatives:* Redis/BullMQ (rejected: extra infrastructure); calling the side effect inside the request (couples latency and correctness). *Trade-offs:* duplicates are possible, so handlers must be idempotent; a job longer than the lease can be redelivered. *At scale:* run several workers (already safe), add a dead-letter view and metrics.
6. **Pagination, indexes, search.** *Chosen:* keyset cursor on `id DESC`, filters in SQL, indexes on team/status, assignee, due date and update time, `ILIKE` search. *Trade-offs:* no sort options; `ILIKE '%x%'` scans. *At scale:* `pg_trgm` or full-text search, compound cursors for other sort orders.
7. **Shared contract.** `shared/types.ts` is imported by the API and the SPA; a test compares real responses with it (exact field set for items, field presence and value types elsewhere). *Alternatives:* OpenAPI/Zod codegen (more tooling than the scope justifies). *Trade-offs:* not a full runtime schema. *At scale:* generate types and validate responses from one schema.
8. **Auth hardening and migrations.** DB-backed login throttling per email+IP, per-token revocation on logout, API security headers, a SPA CSP, a versioned migration runner (needed because these added tables) that refuses databases it cannot positively identify. *Alternatives:* in-memory limiter (breaks with several instances); a full HttpOnly refresh-cookie design (invasive, documented in `docs/SECURITY.md`, not built). *Trade-offs:* one extra indexed lookup per authenticated request; 15-minute sessions. *At scale:* Redis counters, refresh-token families.
9. **UI search and saved filters.** The command palette (Ctrl/Cmd+K) calls the existing team-scoped item search API and only offers item results returned by that endpoint. Saved filter views are namespaced by user ID in browser localStorage; they are explicitly local to that browser and do not imply shared persistence. This adds quick access without a schema migration or a new backend permission surface. Storage errors are surfaced to the user.
10. **Deliberately excluded:** Prisma (engine download blocked in the build environment, so `pg` + raw SQL), Tailwind/shadcn/React Hook Form (plain CSS and controlled forms), refresh tokens, persistent/shared saved views, charts and inferred operational scores (the model lacks the necessary time-series/ownership data), real email, websockets.
